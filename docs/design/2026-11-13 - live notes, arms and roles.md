# Design: live notes on Keeper, git for the skeleton

## Decision

- **Git holds the skeleton.** That is the rules, scripts, templates, skills and pins. Members clone it once and pull it when the rules change.
- **Notes are live.** They live in a Keeper library, and the Seafile app syncs them to every member within minutes.
- **Snapshots go to git.** The owner commits a snapshot of the notes from time to time, for history and rollback.
- **One writer per file.** Seafile does not merge text. When two people change the same file between syncs, it keeps one version and saves the other as a conflict copy, and nobody is told. So every file has exactly one writer, and nothing below ever asks two people to write the same file.

## 1. Where each thing lives

| Place | Holds | Writers |
|---|---|---|
| **Git repository** (skeleton) | `CLAUDE.md`, `conventions.yaml`, `templates/`, `scripts/`, `.claude/`, `.github/`, `sources.yaml`, `environment.yml`, `.mcp.json`, `HOWTO.md`, `MANUAL.md`, `README.md`, `demos/`, `docs/` | Owner (members propose changes by pull request) |
| **Keeper library `astro-kb-data`**, synced to `keeper/` | `pdfs/`, `data/`, `parsed/`, `index/`, **and a new `generated/`**: `Home.md`, `Index - lessons`, `Index - papers`, the `gaia-docs/` table notes, the usage blocks of the code cards | Owner and index keeper. Members get it **read-only** |
| **Keeper library `astro-kb-notes`**, synced to `live/` | One sub-folder per topical arm (§9), each with `notes/`, `lessons/`, `discussion/`, `topics/`; plus the shared `papers/` (with `bibtex/`) and `code/` cards | Members, **read-write** |
| **Each machine only** (git-ignored, not synced) | `outbox/`, `sandbox/`, `index/`, `external/`, `.obsidian/workspace*`, `scripts/config.local` | That machine |

- **The data stays protected.** Keeper sets read-only or read-write per library. So the PDFs and data stay protected, and `files.lock` keeps describing files that do not change. Notes never go in `files.lock`.
- **Obsidian keeps working.** The vault root stays the repository. `keeper/` is synced into it today, and `live/` would be synced the same way, as a real folder with Seafile's "sync with an existing folder". Obsidian finds wikilinks by file name, not by path, so moving the notes into `live/` breaks no links.

## 2. Rules that keep one writer per file

1. **The author is the writer.** A note's `author` in the frontmatter is the only person who changes the file.
   - A `PreToolUse` hook stops Claude from editing any file in `live/` whose `author` is not the user's GitHub name.
   - People editing in Obsidian follow the same rule. The snapshot report (§4) shows any changes to check.
2. **Replies are new files.** A reply to a lesson, a paper note or any other note is a new file:
   - The file is `live/discussion/<target title> - <YYYY-MM-DD HHMM> - <user>.md`, with an `about:` field in its frontmatter that holds a wikilink to the target note.
   - Obsidian's backlinks pane shows the replies on the target note.
   - The "Discussion" section leaves the lesson template. The two existing lessons have empty Discussion sections, so there is nothing to move.
3. **File names cannot clash.**
   - Lessons: `lessons/<date> - <user> - <title>.md`.
   - Digests: `notes/Digest - <topic> - <user> - <date>.md`. A rerun is a new file with `supersedes:`.
   - Paper notes are one per paper. `import_paper.py` first looks for the bibcode in `live/papers/` and stops if the paper is there. The checker reports any duplicate bibcodes, which happen when two people import within one sync interval.
4. **Generated files have one writer: the index keeper's machine.**
   - `Home.md`, the two index notes and the `gaia-docs/` table notes move to `keeper/generated/`, where members can only read.
   - A code card today is written by hand *and* by `fill_code_cards.py`, which is two writers. The generated usage block moves to its own file, `generated/code/<repo> - usage.md`, and the card embeds it with `![[…]]`.
5. **Machine settings never sync.** This covers `.obsidian/workspace*`, the index, the sandbox and `config.local`. The `.obsidian/app.json` change that Obsidian made on its own on 2026-11-12 shows why.
6. **Problems are found and reported.** `check_vault.py` and `doctor.py` report Seafile conflict copies, duplicate bibcodes and duplicate titles, and the session-start hook prints the count.

## 3. Sharing: a local outbox replaces the pull request

The pull request was the point where a check ran and a person looked. With live notes, saving a file into `live/` shares it at once. A draft placed anywhere in `live/` is already shared, so the check must happen **before** the note reaches `live/`:

- **Claude's skills write to `outbox/`.** This applies to `/lesson`, `/digest`, `/consolidate` and paper imports. `outbox/` is local, git-ignored and not synced, but it is inside the vault, so Obsidian shows the drafts.
- **A new `/publish` skill** runs the checks on each file in `outbox/` and moves the files that pass into `live/`. The checks are:
  - `check_vault.py` on the file;
  - the review markers of rule 1 (no proprietary data);
  - the AI-generated callout (rule 6);
  - the one-writer and file-name rules of §2.
- **`/share` stays,** but only for changes to the skeleton, through pull requests to the owner.
- **The remaining risk** is someone writing straight into `live/` from Obsidian, which skips the check. Seafile keeps the history of every file, so the owner can remove a file and its versions.

## 4. Snapshots

- A new script, `scripts/snapshot_notes.py`, for the owner only:
  1. Copy `live/` and `keeper/generated/` to a separate, private repository (`astro-knowledgebase-notes`).
  2. Run `check_vault.py`.
  3. Commit and tag the snapshot as `notes-<date>`.
  4. Write a report of the changes since the last snapshot: new files, changed files, files whose `author` changed, conflict copies, and review-marker hits.
- **Why a separate repository:** a fresh clone of the skeleton then holds no stale notes.
- **When to run it:** once a week, before `/publish-index`.

## 5. Search index

- **On each machine:** each member's machine indexes the live notes as they change. `python -m kb_pkg.index` already adds only what is new.
- **The published index** is still built by the index keeper and copied to `keeper/index/`. It now saves time, and members no longer depend on it.
- **What the index records:** `index_meta.json` records the snapshot tag and a hash of the note list, instead of `kb_commit`.

## 6. `/consolidate` and `/resolve`

- **`/consolidate <topic>`** merges the group's own notes on one topic into a new note, `live/<arm>/topics/Topic - <topic> - <author> - <date>.md` (the author in the name, so two people never write the same file).
  - **Finding the notes:** `applies_to` first, then tags, then `search_kb(source_type="note")`. It shows the list before it writes.
  - **Sections:** current state (each line cited), duplicates, contradictions (side by side, never resolved by Claude), superseded notes, and open questions.
  - **The source notes are never changed.** The frontmatter lists them in `consolidates: [...]`, and the generated Home and indexes mark them "consolidated into …".
  - **Confirmation:** the authors confirm through discussion files.
  - **Reruns** write a new version with `supersedes:`.
- **`/consolidate` with no topic** lists candidates and writes nothing. Candidates are topics with several notes on the same `applies_to`, digests that contradict lessons, and topics with no topic note.
- **`/resolve`** shows each Seafile conflict copy next to its original. The author chooses which to keep. It never merges automatically.

## 8. Order of work

1. Ask the Keeper admins:
   - whether Keeper's Seafile supports file locking (a paid-edition feature);
   - whether the file history records *who* changed a file;
   - whether read-only sharing per library works for the group.
2. Create the library `astro-kb-notes`, empty, read-write for members. Make `astro-kb-data` read-only for members.
3. Change the skeleton (§7) on one branch, with `conventions.yaml` version 2.
4. Run the migration on the owner's machine: move the notes from git into `live/` and the generated notes into `keeper/generated/`, then delete them from git in the same pull request.
5. Make the first snapshot (`notes-2026-11-xx`) and publish the index.
6. Members: pull the skeleton, sync `astro-kb-notes` into `live/`, run `scripts/setup.sh`.
7. After two weeks: read the first snapshot reports for conflict copies and changes against the one-writer rule, and adjust.

## 9. Arms: topical sub-libraries

Added 2026-11-13 after a second discussion. The owner stays the owner of every arm.

### Two kinds of arm

| Kind | Arms | Where | Written by |
|---|---|---|---|
| **Reference** | `gaia-docs` (generated data-model notes), PDFs and parsed text | `keeper/` (the data library, read-only for members) | Scripts, index keeper |
| **Shared** | `papers` (one note per paper), `code` (one card per repository) | `live/papers/`, `live/code/` | The member who imported the paper or wrote the card |
| **Topical** | `binary-stars`, `milky-way`, `hot-stars`, … | `live/<arm>/`, sub-folders of `astro-kb-notes` | Members (one writer per file) |

- **Arms are sub-folders of one library.** All topical arms are sub-folders of the single Keeper library `astro-kb-notes`. The owner shares that library once, read-write. There is no Keeper administration per arm.
- **The data library stays separate,** because it needs different access (read-only for members). Keeper sets access per library. Whether Keeper also supports access per *folder* is not known (§8, step 1). Until then, an arm with a restricted membership would have to become a library of its own.
- **Paper PDFs need a way in.** A member cannot write into the read-only data library. Papers come in by request instead (§10).

### One paper, one copy

- **Papers belong to several arms.** A paper often serves several arms. Its note sits once in `live/papers/`, and its PDF is parsed and embedded once. The importer sets the first arm in the paper note's `arms:`. Further arms are **derived**, not edited: a paper belongs to every arm that has a note citing it. The index keeper writes the result to `keeper/generated/arms/papers.json`. So no member edits another member's paper note to add an arm.
- **Topical notes have one home arm.** Each topical note lives in one arm's folder. It may list other arms in `arms:` so that their searches find it. Nothing is copied.

### Embeddings: one index, every passage labelled

Revised 2026-11-13. This replaces "one index per arm". Updates already process only the changed files, so separate indexes would save almost nothing. They would add a merge step and a model check between tables.

- **One index, one model.** It holds every passage: notes, papers, code and documentation. One embedding model and one chunker, as today. Changing the model means one full rebuild, and only the owner decides that.
- **Each passage carries two labels:**
  - `arm`: the home arm of a note. For a paper, every arm it belongs to: the importer's arm plus the arms whose notes cite it.
  - `source_type`: `note`, `paper`, `code` or `docs`. `docs` is new and covers the Gaia data-model and documentation notes in `keeper/generated/`.
- **The search filters are optional:**
  - `search_kb(query)`: everything. This is the default, for example for the uses of a column across arms.
  - `search_kb(query, arm="milky-way")`: one topic. That arm's notes, plus papers linked to it.
  - `search_kb(query, source_type="docs")`: documentation only. Also `"paper"` and `"code"`.
  - The two filters combine.
- **Column facts are not searched by meaning.** They come from `lookup_column` and `find_columns` (rule 10). A typical question uses both:
  1. `lookup_column` for the table entry;
  2. `search_kb` with no filter for how the column is used.
- **Revisit later** if an arm gets its own members or access rules, or if the index grows too large to search quickly.

### Connections between arms

1. **Shared keys, automatic.** Gaia columns (`applies_to`), bibcodes and `repo@commit` connect notes in all arms. `lookup_column` lists the notes from every arm, next to the papers and code it lists today.
2. **Wikilinks, written by people.** Obsidian resolves a link by file name across the whole vault, so the checker requires file names to be unique across all arms.
3. **Semantic suggestions, generated.** A job of the index keeper finds close passages in *different* arms and writes them to `keeper/generated/related/<arm>.md`. These are suggestions. A person turns one into a wikilink or a `/consolidate` topic.

### Changes to §7

- `conventions.yaml`: a list of `arms`, a tag list per arm, and the field `arms:`.
- `check_vault.py`: file names must be unique across arms, and `arms:` values must be in the list.
- `kb_pkg`: an `arm` label and a `docs` source type on every passage; `arm=` and `source_type=` filters in `search_kb`.
- `import_paper.py`: becomes the curators' ingestion tool (§10).
- New index-keeper job: semantic suggestions between arms.

### First arms

`binary-stars` holds today's lessons and notes. `milky-way` and `hot-stars` start empty. The migration gives every existing paper note `arms: [binary-stars]`. Other arms then come from citations, as described above.

## 10. Adding papers: curators ingest, members request

Added 2026-11-13.

### Roles

| Role | Keeper access | Can |
|---|---|---|
| **Owner** | Both libraries; owns the git skeleton | Everything a curator can, plus the rules, pins and sharing |
| **Curator** | Write to the data library, write to `astro-kb-notes` | Fetch and ingest papers and data; act on requests |
| **Member** | Write to `astro-kb-notes` only | Write notes; request papers |

- **Keeper enforces the roles.** Keeper's access per library is the real control: a member's machine cannot write a PDF into the data library.
- **`keeper/roles.yaml` lists the `curators`.** The skills read this list only to choose which path to offer. It is in Keeper, not in git, because the repository is public (§13). Only the owner can write it, since the data library is read-only for everyone else.

### A member requests a paper

`/request-paper <arXiv id | DOI | bibcode> [arm] [reason]` writes one small file:
`live/requests/<YYYY-MM-DD> - <user> - <id>.md`, with `type: request`, `id`, `arm` and `reason`.

- **Only identifiers.** A request never carries a PDF. That keeps rule 1 (public material only) in the curator's hands.
- **One writer.** The requester is the only writer of the request file.

### A curator ingests

- **`/ingest <id>`** ingests a paper directly. **`/ingest --requests`** lists the open requests and handles the ones the curator chooses.
- **For each paper,** `/ingest`:
  1. checks that the paper is public (arXiv or a published journal), as rule 1 requires;
  2. looks for the bibcode in `live/papers/`, and stops if the paper is there already;
  3. fetches the PDF (arXiv first) into `keeper/pdfs/`, writes the parsed text to `keeper/parsed/`, and updates `files.lock`;
  4. writes the paper note in `live/papers/`, with `author:` the curator, `requested_by:` the requester and `arms: [<arm of the request>]`;
  5. refreshes the `papers` index.
- **A request is closed without editing it.** A request is open while no paper note has its `id`. The index keeper writes a generated list, `keeper/generated/requests.md`, of open, done and declined requests.
- **Declining.** To decline, the curator writes a discussion file with `about:` the request and the reason, for example "not public".
- **The existing script is reused.** `import_paper.py` becomes the curators' tool, with the duplicate check and `requested_by`.

## 11. Fresh start instead of migrating in place

Added 2026-11-13. This replaces §8 steps 3–4 and `scripts/migrations/2_live_notes.py`.

- **New names.** A new git repository, with a new name (the arms go beyond binary stars), and two new Keeper libraries (data, notes). The current repository and Keeper library keep running unchanged until the switch.
- **The skeleton is built new,** starting from the current scripts, skills and templates and adapted to §1–10. The new repository starts with no history.
- **The old repository and the old Keeper library will be deleted** (decided 2026-11-13), and the history of the new repository will be started over before it goes public. So the import must read everything it needs *before* the deletion, and the import is the time to reorganise freely: there is no history to keep compatible.
- **Migration is a one-time import.** A script reads the old repository and the old Keeper library and writes the new layout:
  - each note and lesson goes to `gaia` or `binary-stars` (§12), following a list the owner approves first; lessons are renamed to include the author;
  - paper notes get `arms: [gaia]` (Gaia Collaboration and DPAC papers) or `arms: [binary-stars]`;
  - code cards are split from their generated usage blocks;
  - the generated notes are regenerated;
  - every arm is embedded fresh with one model.
- **The switch.**
  1. Freeze the old repository: no more merges.
  2. Run the import.
  3. Make the first snapshot.
  4. Members clone the new skeleton and sync the new libraries.
  5. Check the import (checker, a search for a few known notes), then delete the old repository and the old Keeper library.

## 12. The Gaia arm: a foundation for every arm

Added 2026-11-13. The old knowledge base mixed two things: what Gaia says (documentation, data model, validation, the Gaia Collaboration papers) and binary-star science. Every arm needs the first; only one arm needs the second.

- **A foundation arm `gaia`** (`foundation: true` in `conventions.yaml`). It holds notes, lessons, topics and discussion like any arm. Its label also goes on the generated documentation (`docs_arm: gaia`) and on the papers that its notes cite or that a curator ingests for it.

  | `gaia` | a science arm, e.g. `binary-stars` |
  |---|---|
  | data model and documentation (generated) | the astrophysics |
  | Gaia Collaboration and DPAC papers | papers that use Gaia for science |
  | lessons on columns, flags, units, `corr_vec`, selection criteria | lessons on a paper's error, a method, a population |
  | validation tables: Gaia values against independent catalogues | notes that connect the two, e.g. a mass from a DR3 orbit |

- **Links run one way, from the science arms into `gaia`.** The checker refuses a `gaia` note with a link (in the text, or in `about:`, `consolidates:`, `supersedes:`) to a note of a non-foundation arm. Links to shared papers and code cards are allowed. So the Gaia arm stays complete without any science arm, and a Milky Way member can use it without binary-star notes in the way.
- **The reverse view is generated, not written.** `lookup_column` lists the notes of every arm that use a column: by `applies_to:` or by a link to the column's data-model note. Obsidian's backlinks show the same for wikilinks.
- **Tags.** The Gaia tags (`NSS`, `DataModel`, `Validation`, …) may be used in every arm, because science notes are about Gaia products too. Tags describe a note; the arm decides where it lives and who searches it.
- **Search.** `arm="gaia"`: everything about Gaia (notes, papers, documentation). `source_type="docs"`: the documentation only.

## 13. A public skeleton, closed Keeper libraries

Added 2026-11-13.

- **The git repository is public.** The rules, scripts, skills and templates are a method others can reuse. Members can clone without a GitHub invitation.
- **The Keeper libraries stay closed.** The notes, papers, data, indexes and the member list are there.
- **What keeps private things out of git:**
  1. `scripts/check_public.py` refuses files outside the skeleton, PDFs, data, images and archives, files over 1 MB, tokens and keys, and e-mail addresses (other than `example.org` and noreply). It runs before `/share` (`--staged`) and on every pull request.
  2. The curator list is in `keeper/roles.yaml`, not in `conventions.yaml`.
  3. `.obsidian/bookmarks.json` is not in git: bookmarks name private notes.
  4. The snapshot repository of the notes (§4) is **private**.
- **Only the owner merges.** CODEOWNERS and branch protection on `main`. This matters more in public: the hooks and `.mcp.json` run code on every member's machine, and anyone can open a pull request.
- **Squash merges only.** A file added and removed inside a pull request then never reaches the history of `main`.
- **Licences.** MIT for the code (`LICENSE`), CC BY 4.0 for the text (`LICENSE-docs.md`). Neither covers the content in Keeper.
- **Code pins.** `sources.yaml` names the code repositories and commits that are indexed. They are all public today. A private repository must not be pinned there.

## Open questions

- Whether Keeper supports access per folder. If it does, the data library and `astro-kb-notes` could become one library, and arms could have restricted members.
- If Keeper has file locking, a few shared hub notes could allow more than one writer.
- If the Seafile history records the person who made each change, the snapshot report can name them. Otherwise it can only show that a file changed.
- `demos/` stay in git, since they are reviewed examples. A notebook a member wants to share would then still go through a pull request.
- How often to snapshot: weekly, or at each `/publish-index`.
